# MIX-STQ v0.24 인코더 감사: 제 IQ3_XXS는 저장 불가능한 블록을 만들고 있었습니다

**작성일** 2026-08-31
**후속 결과 (v25)** 참조 IQ3_XXS를 Qwen3.8-27B에 적용한 정확도는 0.7700으로,
dense FP16 0.8050보다 3.5%p 낮았습니다. p=0.1185와 CI [0.0, 7.5]%p는 유의한
손실과 동등성 어느 쪽도 확정하지 못합니다. 참조 IQ2가 없으므로 IQ3 대 IQ2의
실제 형식 간 우위도 미확정입니다. `docs/mix-stq-v25-reference-iq3.md` 참조.

**결론** **자기 정정입니다.** v19–v23의 모든 정확도 측정에 쓰인
`torch_iq2.quantize_rows(tier="iq3_xxs")`는 IQ3_XXS 형식이 표현할 수 없는 상태를
만듭니다. 부호 패리티 제약과 서브블록 공유 스케일 제약을 구현하지 않았습니다.
그 결과 실제 오차를 **3.5–3.7배 과소평가**했습니다.
핵심 결론(IQ3_XXS가 IQ2_XXS보다 낫다)은 참조 IQ2가 나올 때까지 **보류합니다.**

---

## 1. 감사 동기

v23까지 "다음 우선순위는 GGUF 왕복과 C 디코더 패리티"라고 반복해 적었습니다.
그 작업을 시작하면서 `ggml-quants.c`의 실제 `quantize_row_iq3_xxs_impl`
(3938행)을 읽었고, 제 인코더가 **다른 알고리즘**임을 발견했습니다.
단순한 구현 차이가 아니라 제약 조건이 빠져 있었습니다.

## 2. 발견: 두 개의 누락된 제약

독립 참조 구현(`src/mixstq/iq3_reference.py`, C 소스를 충실히 포팅)으로
제 인코더 출력을 검사한 결과입니다. 시드 고정 (8, 512) 텐서, 1024 레인.

| 검사 항목 | 결과 | 판정 |
|---|---:|---|
| 크기 코드워드가 그리드에 존재 | 0 / 1024 off-grid | **통과** |
| 부호 패리티 유효 | **502 / 1024 레인 무효** | **실패** |
| 서브블록 공유 스케일 | **128 / 128 그룹 위반** | **실패** |

**제약 1: 부호 패리티.** IQ3_XXS는 8개 값당 부호를 **7비트**로 저장합니다
(`block_signs[k] = s & 127`). 8번째 부호는 짝수 패리티로 암시됩니다. C 코드는
음수 개수가 홀수면 `weight*x^2`가 최소인 항목을 한 번 더 뒤집어 패리티를
맞춥니다. 제 인코더는 이 단계가 없어 부호 패턴 절반이 인코딩 불가입니다.

**제약 2: 공유 스케일.** 블록당 fp16 스케일 하나가 32개 값 서브블록 전체에
공유됩니다. 제 해석해는 **4개 값 레인마다 자유 스케일**을 부여했습니다.
이것이 v20에서 "격자 탐색보다 오차가 낮다"고 관측한 이유의 상당 부분입니다.
저는 더 넓은 공간에서 최적화하고 있었습니다.

## 3. 오차 과소평가 규모

| 텐서 | 실제 IQ3_XXS | 제 IQ3_XXS | 과소평가 | 제 IQ2_XXS |
|---|---:|---:|---:|---:|
| (8, 512) seed 7 | 0.029034 | 0.008232 | **3.53배** | 0.063023 |
| (4, 2048) seed 11 | 0.029607 | 0.007960 | **3.72배** | 0.062844 |

제 인코더의 0.0083은 형식이 담을 수 없는 상태의 오차이므로 **의미가 없습니다.**
실제 IQ3_XXS 오차는 0.029 수준입니다.

## 4. 무엇이 무효이고 무엇이 살아남는가

정직하게 구분합니다.

### 무효

- **v20의 "해석해가 격자 탐색보다 오차가 낮다"** (0.0086 → 0.0084 등).
  격자 탐색은 ggml의 31점 스케일 탐색을 모방한 것이었고, 제 해석해가 이긴 것은
  제약을 위반해서였습니다. 이 비교는 성립하지 않습니다.
- **모든 `mean_error` 절대값.** v19–v23에 기록된 IQ2/IQ3 티어의 재구성 오차는
  실제 형식의 오차가 아닙니다. IQ2_XXS도 같은 두 제약을 공유하므로
  (C 소스 3294행, 동일한 패리티·공유 스케일 구조) 마찬가지입니다.
- **v21의 "오차 순위 역전" 분석.** 오차 자체가 형식과 무관하므로 근거가 약합니다.

### 탐색 범위에서만 살아남음

- **IQ3_XXS가 IQ2_XXS보다 낫다는 가설.** 참조 IQ3 오차 0.029가 IQ2 근사
  0.063보다 낮다는 관측은 후속 가설로 남습니다. 한쪽만 참조 구현이므로 실제
  형식 간 오차나 정확도 순서를 확정하지 않습니다.
- **정확도 측정의 상대 비교.** v22의 "IQ3_XXS는 dense FP16과 구별 불가, IQ2_XXS는
  유의하게 손실"은 세 팔이 **동일한 근사 인코더**를 통과했으므로 팔 간 비교로는
  유효합니다. 실제 형식이나 배포 팔의 비교로 확장하지 않습니다.
- **비트 예산이 코드북보다 지배적이라는 결론.** 이것은 티어 간 비교이며
  근사가 양쪽에 동일하게 적용되었습니다.

### 불확실

**참조 IQ3_XXS는 재측정됐지만 동등성은 여전히 미확정입니다.** v25에서 0.7700으로
dense FP16보다 3.5%p 낮았고, 95% CI는 dense 우위 [0.0, 7.5]%p였습니다.
유의한 손실 기준은 통과하지 않았지만 “차이 없음”을 지지할 정밀도도 아닙니다.

## 5. 왜 이걸 놓쳤는가

세 가지가 겹쳤습니다.

**형식 검증 테스트가 없었습니다.** `test_tier_encoders.py`는 bpw 값과 오차
단조성만 확인했습니다. "출력이 실제로 이 형식으로 저장 가능한가"를 묻지
않았습니다. 이번에 추가한 `test_iq3_reference.py`가 그 검사입니다.

**낮은 오차를 성공 신호로 읽었습니다.** v20에서 해석해가 격자 탐색을 이겼을 때
"격자가 최적점을 놓치고 있었다"고 결론했습니다. 실제로는 제가 제약을 위반해
더 넓은 공간을 탐색한 것이었습니다. **더 좋은 숫자가 나오면 의심해야 했습니다.**

**GGUF 검증을 계속 뒤로 밀었습니다.** v19부터 v23까지 다섯 번 "다음 우선순위"로
적으면서 실행하지 않았습니다. 그 작업이 바로 이 결함을 드러냈습니다.

## 6. 검증 로그

| 주장 | 근거 | 상태 |
|---|---|---|
| 참조 구현이 C 소스에 충실 | 패리티 강제, 31점 스케일 탐색, 레인 수복, `GROUP_MAX_EPS_IQ3_XXS` 1e-8 모두 포팅 | 확인 |
| 크기 코드워드는 정상 | 0/1024 off-grid | 확인 |
| 부호 패리티 위반 | 502/1024 레인 | 확인 |
| 공유 스케일 위반 | 128/128 그룹 | 확인 |
| 오차 3.5–3.7배 과소평가 | 두 텐서, 두 시드 | 확인 |
| 실제 IQ3 < 제 IQ2 근사 | 0.029 vs 0.063, 두 텐서 | 확인 |
| 오프라인 스위트 | 10/10 통과, ruff 통과 | 확인 |

### 측정하지 않은 것

- **참조 인코더로 정확도 재측정.** 가장 중요한 후속 작업입니다. 참조 구현은
  순수 파이썬이라 27B 192텐서에 적용하려면 벡터화 또는 GPU 포팅이 필요합니다.
- **IQ2_XXS 참조 구현.** C 소스(3294행)를 읽어 동일 구조를 확인했으나
  포팅하지 않았습니다. IQ2 계열 오차도 같은 방향으로 틀렸을 것입니다.
- **이웃 탐색 방식 차이.** 참조 구현은 256개 그리드 전수 탐색을 쓰고 ggml은
  사전 계산된 이웃 테이블을 씁니다. 결과가 동일한지 확인하지 않았습니다.
- **GGUF 왕복.** 여전히 미실행. 이제 참조 인코더가 있어 가능합니다.

## 7. 다음에 할 일

1. **참조 인코더를 벡터화해 정확도를 재측정합니다.** v22의 27B 결과를
   실제 IQ3_XXS로 다시 재면 "dense FP16과 구별 불가"가 유지되는지 확정됩니다.
   이것이 이 연구의 핵심 주장이므로 최우선입니다.
2. **IQ2_XXS 참조도 포팅합니다.** 티어 간 비교의 근거를 실제 형식으로 옮깁니다.
3. **문서에 정정을 반영합니다.** v19–v23의 `mean_error` 값에 이 문서를
   가리키는 주석을 답니다.

**하지 않을 것**: 근사 인코더를 "고쳐서" 제약을 만족시키기. 이미 참조 구현이
있으므로 그것을 쓰는 것이 맞습니다. 근사는 빠른 탐색용으로만 남깁니다.
