# MIX-STQ v1.2 — GGUF 컨테이너 구현 및 왕복 검증

**작성일** 2026-08-30
**GPU 지출** $0 (CPU + HTTP Range read)
**결론** v1.0이 "미구현"으로 남긴 GGUF 컨테이너가 **동작합니다.** 실제 가중치에서 왕복 검증 통과.

---

## 1. 무엇이 필요했는가

v1.0의 미검증 항목: "GGUF 컨테이너 미구현. llama.cpp가 32바이트 코드북 헤더를
읽는 패치가 필요합니다."

핵심 설계 문제는 **코드북을 어디에 두느냐**입니다. GGUF의 텐서 데이터 영역은
블록 배열이어야 하므로 텐서마다 다른 32바이트 헤더를 끼워 넣을 자리가 없습니다.

## 2. 해결: 텐서별 KV 메타데이터

코드북을 **텐서 이름으로 키가 붙는 uint8 배열 KV**로 저장합니다.

```
ltc.codebook.<tensor_name>  : uint8[32]   패턴 인덱스 (밑 3의 4자리, 0..80)
ltc.block_size              : uint32 256
ltc.block_bytes             : uint32 42
ltc.codebook_bytes          : uint32 32
```

텐서 데이터 영역은 **STQ1_0과 완전히 동일한 42바이트 블록 배열**로 유지됩니다.
llama.cpp 패치는 dequantize 함수가 텐서 이름으로 KV를 조회해 코드북을 얻는 것만
추가하면 됩니다. 블록 파싱 로직은 손댈 필요가 없습니다.

## 3. 왕복 검증 결과

실제 OLMoE 가중치(레이어 0 expert 0 gate_proj) 16,384개, 64블록:

| 항목 | 값 |
|---|---:|
| 코드북 헤더 | 32 바이트 |
| 페이로드 | 2,688 바이트 (64 x 42) |
| 논리 저장량 | 2,720 바이트 = **1.3281 bpw** |
| GGUF 파일 총량 | 3,104 바이트 (헤더 + 정렬 패딩 포함) |

통과한 불변식:

| 검증 | 결과 |
|---|---|
| 코드북이 uint8 KV로 보존 | PASS |
| 페이로드 바이트 단위 동일 | PASS |
| 컨테이너 디코드 == 직접 디코드 (완전 일치) | PASS |
| ggml 타입 ID 40 보존 | PASS |
| 블록 기하 메타데이터 유지 | PASS |

동일 텐서에서 품질도 확인했습니다.

| 코덱 | 상대오차 |
|---|---:|
| STQ1_0 | 0.2653 |
| **LTC** | **0.2298** |
| 차이 | **−13.4%** |

## 4. bpw에 대한 정직한 기록

1.3281 bpw는 STQ1_0의 1.3125보다 **0.0156 높습니다.** 32바이트 코드북이
16,384 가중치에 분산된 결과입니다.

| 텐서 크기 | LTC bpw | STQ1_0 대비 증가 |
|---:|---:|---:|
| 16,384 (이번 테스트) | 1.3281 | +1.19% |
| 2,097,152 (실제 expert) | 1.3126 | +0.01% |

**실제 expert 텐서 규모에서는 무시 가능하지만, 작은 텐서에서는 측정 가능합니다.**
v1.0이 기록한 1.3151 bpw도 같은 이유입니다.
