## 1. 가장 중요한 결과: 합성 importance가 이득을 2배 과장했습니다

실제 활성화 imatrix를 수집해 LTC 이득을 재측정했습니다. OLMoE expert 텐서 24개
(레이어 0–11 × gate/up), 동일 가중치에 대해 **실제 importance와 합성 importance만 교체**한
통제 비교입니다.

| 조건 | 평균 LTC 이득 | 최소 | 최대 |
|---|---:|---:|---:|
| **실제 imatrix** | **+6.5%** | +3.5% | +12.6% |
| 합성 importance | +12.9% | +11.6% | +14.3% |
| 차이 | **−6.4 pp** | | |

**게이트 판정: PASS** (기준 >5%). 24개 텐서 전부 양의 이득이며, 부호가 뒤집힌 텐서는 없습니다.

투영별 차이도 드러났습니다:

| 투영 | 실제 imatrix 이득 |
|---|---:|
| `gate_proj` | +7.4% |
| `up_proj` | +5.6% |

`gate_proj`가 일관되게 더 큰 이득을 봅니다. v0.3c에서 "LTC 이득은 균일하므로 전 텐서
균일 적용"이라고 결론냈는데, 이는 **합성 importance 기준이었습니다.** 실제로는 투영 역할에
따라 다르므로 gate/up을 구분할 여지가 있습니다.

### 왜 과장되었는가

실제 imatrix의 동적 범위는 **3.1e+06**입니다 (L0: max 2.01, min 6.57e-07).
제 합성 importance는 |N(0,1)|² 로 범위가 훨씬 좁고 균일합니다.

실제 importance는 소수 채널에 극단적으로 집중되어 있어 **오차가 그 채널들에 의해 지배됩니다.**
LTC의 강점은 0 비율을 자유롭게 늘리는 것인데, 고importance 채널은 대부분 0이 아니어야 하므로
자유도의 이득이 줄어듭니다. LTC 0 비율도 실제 기준에서 0.414–0.498로 관측되었습니다.

**설계 기대치를 다시 교정합니다: 13–14% → 약 6–7%.**

## 2. IQ2_XXS 인코더 구현 (v0.4 선행 항목 완료)

v0.2에서 제 7레벨 프록시가 "충실하지 않다"고 기록했던 것을 실제 구현으로 대체했습니다.
llama.cpp의 실제 테이블을 파싱해 사용했습니다.

| 항목 | 값 | 출처 |
|---|---|---|
| 블록 크기 | 256 가중치 | `block_iq2_xxs` |
| 저장 | 2바이트 scale + 32×uint16 = **66바이트** | 구조체 정의 |
| bpw | **2.0625** | 66×8/256 |
| grid | 256 항목 × 8값, 크기 {8, 25, 43} | `iq2xxs_grid` |
| sign 테이블 | 128 × 8 | `ksigns_iq2xs`, `kmask_iq2xs` |
| sub-scale | 4비트, `d*(0.5+level)*0.25` | `dequantize_row_iq2_xxs` |

검증 6항목 통과. 특히 grid 항목 하나로만 채운 블록은 상대오차 **8.7e-05**로 재구성되어
인코더가 형식을 정확히 구현했음을 확인했습니다.

작업 중 제 테스트가 틀렸던 것도 발견했습니다: 서로 다른 크기(8/25/43)를 한 lane에 섞은 입력이
4.85% 오차를 냈는데, 이는 인코더 버그가 아니라 **lane마다 scale이 하나뿐인 형식의 성질**입니다.
테스트를 실제로 달성 가능한 조건으로 교정했습니다.

### 교정된 오차비

| 비교 | 7레벨 프록시 (v0.2) | 실제 IQ2_XXS (v0.3c) |
|---|---:|---:|
| STQ1_0 / IQ2_XXS | 3.9배 (상한이라고 기록) | **4.32배** |
| LTC / IQ2_XXS | — | 3.76배 |

프록시는 방향은 맞았지만 **과소평가**였습니다. 실제 IQ2_XXS는 STQ1_0보다 4.32배 정확합니다
(비트는 1.57배). 이는 HY4가 왜 대부분 레이어를 IQ2로 올렸는지 설명합니다.

## 4. 발견한 구현 문제 세 가지

### transformers 5.16이 expert를 융합한다

첫 imatrix 시도가 `no target linear layers matched`로 실패했습니다. 체크포인트에는
`experts.0.gate_proj.weight` 같은 이름이 365개 있지만, **로드된 모델에는 per-expert
`nn.Linear`가 존재하지 않습니다.** transformers 5.16은 64개 expert를 하나의
`OlmoeExperts` 모듈로 융합하며 파라미터는 `gate_up_proj (64, 2048, 2048)`입니다.

수정: 모듈 이름 접미사(`mlp.experts`, `mlp.gate`)로 후킹하고, 융합 레이아웃에서
채널별 E[x²]와 router 통계를 함께 수집합니다. 이 구조 변경 덕분에
**router 히트를 무료로 얻었고**, 그것이 위의 coverage 계측을 가능하게 했습니다.

### vast.ai 검색 API가 무작위 슬라이스를 반환한다

`GET /bundles/`는 인증과 무관하게 64개 샘플만 반환합니다. 실제 검색은
`POST /bundles`에 **평탄한 쿼리**(`q` 래퍼 없이, 8개 미만 연산자)를 보내야 합니다.

더 중요한 발견: 동일 쿼리를 3회 호출하면 **합집합 128개, 교집합 24개**입니다.
특정 offer ID는 3회 중 1회만 나타났습니다. 따라서 "검색 → ID로 생성" 흐름은 본질적으로
경쟁 조건이며, 제 가격 상한 검증이 이 때문에 정상 offer를 거부했습니다.

### 비용 표시가 31일치를 내 지출로 보고했다

`list`가 `cost_so_far: $115.71`을 표시했습니다. 원인은 vast.ai의
`duration` 필드가 **머신의 총 가동시간**(44,630분 ≈ 31일)이라는 점입니다.
`start_date` 기준으로 고쳐 실제 임대 시간만 계산합니다. 계정 credit으로 교차 확인했습니다:
$2.4031 → $2.2613, 차이 $0.1418 (인스턴스 비용 + 스토리지).
