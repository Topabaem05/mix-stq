# MIX-STQ v1.4 — ggml_vec_dot_ltc1_0 구현 및 성능 경로 확립

**작성일** 2026-08-30
**GPU 지출** $0 (CPU only)
**결론** 성능 경로가 동작합니다. 융합 내적이 dequantize 경로보다 **2.37배 빠릅니다.**

---

## 1. 왜 필요했는가

v1.3에서 "dequantize만으로는 llama.cpp가 모델을 실행할 수 없다. 실제 추론에는
양자화 가중치를 직접 소비하는 `vec_dot`이 필요하며 그것이 성능의 핵심"이라고
기록했습니다. 그 항목을 구현했습니다.

## 2. 구현: 역양자화 없는 융합 내적

```c
void ggml_vec_dot_ltc1_0(int64_t count, float *result, const block_ltc1_0 *blocks,
                         const ltc_codebook *book, const float *activations);
```

핵심은 **역양자화된 행을 메모리에 만들지 않는 것**입니다. 코드북 항목이 삼진
{−1,0,+1}이므로 곱셈 없이 부호 있는 누산으로 처리할 수 있습니다.

```c
block_sum += entry[0]*act[0] + entry[1]*act[1] + entry[2]*act[2] + entry[3]*act[3];
total += scale * block_sum;   // 스케일은 블록당 한 번만
```

스케일 곱을 블록 단위로 밀어낸 것이 중요합니다. 256개 가중치마다 곱셈 1회입니다.

## 3. 정확성 검증

실제 OLMoE 가중치 65,536개(256블록), 학습된 코드북:

| 경로 | 내적 값 |
|---|---:|
| Python float64 참조 | −2.690699 |
| C 융합 vec_dot | −2.690697 |
| C dequantize-then-dot | −2.690698 |

| 비교 | 상대 오차 |
|---|---:|
| 융합 vs Python float64 | **6.021e-07** |
| 융합 vs C dequantize 경로 | **−4.430e-07** |

float32 누산의 정상 범위입니다. v1.3의 dequantize는 비트 단위 일치였지만,
내적은 누산 순서가 다르므로 비트 일치가 아니라 **수치적 동등**이 올바른 기준입니다.

## 4. 성능: 융합이 2.37배 빠릅니다

65,536 가중치 x 200회, Intel i5-4278U:

| 경로 | 처리량 | 비교 |
|---|---:|---:|
| dequantize + dot | 289.7 Mw/s | 기준 |
| **융합 vec_dot** | **686.4 Mw/s** | **2.37배** |

이유는 메모리입니다. dequantize 경로는 65,536개 float32(256 KB)를 쓰고 다시 읽습니다.
L2가 256 KB인 이 CPU에서 캐시를 완전히 밀어냅니다. 융합 경로는 42바이트 블록만
읽고 누산기에서 처리하므로 중간 버퍼가 없습니다.

**v1.1에서 측정한 디코드 속도(−17.9%)는 dequantize 경로 기준이었습니다.**
실제 추론은 vec_dot을 쓰므로 그 수치가 곧 추론 성능은 아닙니다.
