## 1. 코드 확인으로 해결된 항목: v1.0은 4-lane이었다

v1.1에서 디코드 속도를 측정했을 때 4-lane과 8-lane이 갈렸습니다.

| 구성 | LUT | 처리량 | STQ1_0 대비 |
|---|---:|---:|---:|
| 4/5 32항목 | 128 B | 1036.5 Mw/s | **동일 비용** |
| 8/10 1024항목 | 8 KB | 851.4 Mw/s | −17.9% |

v1.0의 품질 결과가 어느 구성인지 문서에 명시되지 않아 GPU 재측정을 검토했으나,
소스 확인으로 해결됐습니다.

```
codebook.py:  LANES = 4, CODE_BITS = 5, CODEBOOK_SIZE = 32
ltc_format.py: BLOCK_BYTES = 42, LTC_BPW = 1.3125
```

**v1.0의 ppl −13.9%는 4-lane 구성입니다.** 4-lane은 STQ1_0과 동일한 32항목/128바이트
LUT를 쓰므로 디코드 비용이 같습니다. 따라서 확립된 주장은 다음과 같이 강화됩니다.

> 동일 비트, 동일 파일 크기, **동일 디코드 비용**에서 perplexity 13.9% 개선.

v1.1이 측정한 −17.9%는 8-lane 실험 구성에만 해당하며, 현재 출하 구성의 특성이 아닙니다.

## 3. 다음 연구 우선순위

기준은 "이 결과가 틀리면 무엇이 무너지는가"입니다.

| 순위 | 연구 | 추정 비용 | 틀렸을 때의 파급 |
|---|---|---:|---|
| 1 | 태스크 정확도 (MMLU + ARC-Challenge) | ~$0.35 | 가치 제안 붕괴 |
| 2 | Qwen1.5-MoE 품질 교차 검증 | ~$0.30 | OLMoE 한정으로 축소 |
| 3 | 8-lane 품질 (상한 탐색) | ~$0.20 | 없음 (탐색적) |

### 1순위가 결정적인 이유

현재 모든 품질 증거가 perplexity, logit KL, top-1, margin, router입니다.
**태스크 정확도는 한 번도 측정하지 않았습니다.**

두 개의 독립적 근거가 같은 경고를 합니다.

- SchurQuant(arXiv:2608.15567): 2-bit에서 zero-shot +11.88 pp를 얻으면서도
  "높은 정밀도에서는 더 조밀한 재구성이 종단 지표를 일관되게 개선하지 않는다"
- Qwen3.8-27B 외부 측정: 1-bit가 top-1 76%인데 **태스크는 무작위 추측 수준 붕괴**.
  arXiv:2608.06564의 margin 붕괴(2비트에서 배율 중앙값 0.00)와 같은 현상

즉 "LTC가 실제로 유용하다"는 주장의 **유일한 미검증 고리**입니다.
차이가 사라지면 MIX-STQ는 "perplexity만 개선하는 코덱"으로 축소됩니다.

설계: OLMoE에 dense / mixed STQ1_0 / mixed LTC 3-arm, 동일 1.875 bpw, 동일 레이어 배치,
MMLU 부분집합 + ARC-Challenge, **쌍 McNemar 검정**(v1.0의 쌍 부트스트랩과 동일한 규율).

### 수행하지 않을 것

| 항목 | 이유 |
|---|---|
| GPU 커널 최적화 | 엔지니어링이며 연구 결론을 바꾸지 않음 |
| QAT 결합 | 학습 비용이 잔여 credit 초과 |
| 레이어 배분 재시도 | v0.8에서 이미 반증 |
| 선택기 고도화 | v0.3e에서 −0.1%로 무효 확인 |

## 4. 예산과 블로커

잔여 credit $0.9792. 1–3순위 합계 약 $0.85.
이전 세션 실적(RTX 3090, 25–61분, $0.065–$0.16)에 근거한 추정입니다.

**블로커: vast.ai 키가 현재 세션 환경에 없습니다.**
`~/.vast_api_key` 부재, `MIXSTQ_VAST_KEY` 미설정. 이전 세션들(v0.3–v1.0, 총 $1.16)의
키는 이 세션에 전달되지 않았습니다.

```bash
export MIXSTQ_VAST_KEY='...'
```

진행 절차: offer 탐색(무료·읽기 전용) → dry-run → `--confirm` 생성 → 작업 → 즉시 destroy.
`vast_control.py`는 기본이 dry-run이며 `--confirm` 없이는 API를 호출하지 않고,
`--max-hourly` 상한 초과 offer는 거부합니다.
