**작성일** 2026-08-29
**결론** v0.2 게이트 **통과**. 설계 전제가 실제 모델 가중치에서 확인되었습니다.

## 1. v0.2 게이트: 실제 가중치 검증

설계 문서 §6에서 "v0.2가 게이트"라고 명시했습니다. 실제 expert 가중치의 자연 0 비율이
25%에 가까우면 3:4 제약은 손실이 아니고 설계 근거가 사라집니다. 이를 측정했습니다.

**방법**: GPU나 전체 다운로드 없이, safetensors 헤더를 파싱하고 HTTP Range 요청으로
필요한 텐서만 가져왔습니다 (`remote_weights.py`). 13.84 GB 샤드에서 실제로 전송한 것은
텐서 8개, 약 33 MB입니다. BF16은 상위 16비트 시프트로 float32로 승격했습니다.

**대상**: `allenai/OLMoE-1B-7B-0924` — 64 expert MoE, 레이어 0/4/8 × expert 0/3 ×
gate/up 투영. 총 16,777,216개 실제 가중치.

### 결과

| 텐서 | 자연 0 비율 | STQ1_0 | LTC | 개선 | LTC 0 비율 |
|---|---:|---:|---:|---:|---:|
| L0.e0.up | 0.316 | 0.2491 | 0.2174 | +12.7% | 0.497 |
| L0.e3.gate | 0.312 | 0.2480 | 0.2142 | +13.6% | 0.485 |
| L0.e3.up | 0.314 | 0.2495 | 0.2145 | +14.0% | 0.488 |
| L4.e0.gate | 0.315 | 0.2527 | 0.2180 | +13.7% | 0.489 |
| L4.e0.up | 0.312 | 0.2442 | 0.2105 | +13.8% | 0.486 |
| L4.e3.gate | 0.312 | 0.2476 | 0.2136 | +13.7% | 0.486 |
| L4.e3.up | 0.311 | 0.2426 | 0.2095 | +13.7% | 0.484 |

**게이트 판정**

| 지표 | 값 | 기준 | 판정 |
|---|---:|---|---|
| 평균 자연 0 비율 | **0.313** | > 0.30 | 통과 |
| 3:4가 강제하는 값 | 0.250 | — | — |
| 평균 LTC 개선 | **+13.5%** | > 5% | 통과 |
| 개선 범위 | +12.7% ~ +14.0% | — | 매우 일관됨 |
| 평균 LTC 0 비율 | 0.487 | — | — |

**해석**: 실제 expert 가중치는 31.3%를 0으로 만들고 싶어 하는데 3:4는 25.0%로 막습니다.
LTC는 이 상한을 풀어 48.7%까지 사용하며 오차를 13.5% 낮춥니다.

개선폭이 12.7–14.0%로 **매우 좁습니다.** 이는 LTC 이득이 특정 레이어의 우연이 아니라
**모든 expert 텐서에 공통된 구조적 성질**임을 시사합니다. 합성 Gaussian 예측치(14.2%)와도
거의 일치합니다.

### 합성 예측 대비 실제

| 분포 | 합성 예측 | 실제 측정 |
|---|---:|---:|
| Gaussian | +14.2% | — |
| Laplace | +23.0% | — |
| sparse + outlier | +63.3% | — |
| **OLMoE 실제 expert** | — | **+13.5%** |

실제 가중치는 Gaussian에 가깝고, heavy-tail 시나리오의 큰 이득(23–63%)은 나타나지 않았습니다.
설계 문서의 낙관적 수치를 **실측치로 교정합니다: 기대 이득은 약 13–14%입니다.**

이는 §6 측정의 −40% 임계값에 미치지 않으므로, **레이어 배분은 변하지 않고**
이득은 품질 또는 파일 크기로 받게 됩니다(설계 §4 결론과 일치).

## 2. 남은 한계: importance가 아직 합성입니다

v0.2에서 **가중치는 실제**지만 importance는 여전히 무작위입니다. 실제 imatrix는
활성화 통계이므로 모델 forward 실행이 필요하고, 그래서 GPU가 필요합니다.

이것이 vast.ai를 쓰는 이유입니다.

## 3. vast.ai 실행 하네스

`work/mixstq/vast_control.py` — API 직접 호출(CLI 설치 불필요), 비용 상한 강제.

### 안전 설계

| 보호 | 동작 | 검증됨 |
|---|---|---|
| 기본 dry-run | `--confirm` 없으면 **API를 아예 호출하지 않음** | 예 |
| 시간당 상한 | `--max-hourly` 초과 offer는 생성 거부 | 코드 경로 |
| 키 검증 | 잘못된 키는 명확한 auth 오류 | 예 |
| HTML 응답 감지 | 오류 페이지를 JSON으로 오해하지 않음 | 예 |
| 비용 추적 | `list`가 인스턴스별 누적 지출 표시 | 코드 경로 |
| 감사 로그 | 생성/파괴를 `vast_state.json`에 기록 | 코드 경로 |

키 설정:

```bash
export MIXSTQ_VAST_KEY='...'    # 또는 ~/.vast_api_key
```

### 사용

```bash
# 1. offer 탐색 (무료, 읽기 전용)
python3 vast_control.py search --gpu RTX_4090 --max-price 0.50 --min-vram 24 --disk 80

# 2. dry-run (돈 쓰지 않음, API 호출 없음)
python3 vast_control.py create --offer <ID> --max-hourly 0.50

# 3. 실제 생성 (명시적 확인 필요)
python3 vast_control.py create --offer <ID> --max-hourly 0.50 --confirm

# 4. 상태와 누적 비용
python3 vast_control.py list

# 5. 반드시 파괴
python3 vast_control.py destroy --id <INSTANCE_ID> --confirm
```

### 권장 사양과 예상 비용

| 작업 | GPU | VRAM | 디스크 | 예상 시간 | 예상 비용 |
|---|---|---:|---:|---:|---:|
| OLMoE-1B-7B imatrix | RTX 4090 | 24 GB | 80 GB | ~30분 | ~$0.25 |
| Qwen3-30B-A3B imatrix | A100 40GB | 40 GB | 200 GB | ~1.5시간 | ~$1.50 |
| GGUF 변환 + PPL | RTX 4090 | 24 GB | 150 GB | ~1시간 | ~$0.50 |

**비용 규율**: 작업 시작 전 예상 비용을 계산하고, 완료 즉시 `destroy`합니다.
Pacific의 기록에는 GPU 세션을 놓쳐 $2.41을 출력 없이 태운 사례가 있습니다.

## 4. GPU 워커: 실제 imatrix 수집

`work/mixstq/collect_imatrix.py` — forward hook으로 각 gate/up/down 입력의
채널별 (mathbb{E}[x^2])를 수집합니다.

**GPU 비용을 쓰기 전에 로컬 CPU에서 훅 수학을 검증했습니다** (`test_imatrix_hook.py`):

```
PASS: imatrix hook math verified on CPU
  6 linears hooked (gate/up/down x 2 blocks)
  row accounting exact: 42 rows
  E[x^2] matches manual computation (atol 1e-5)
  down_proj correctly sees hidden dim (32), gate/up see model dim (16)
  all values finite and non-negative
```

`down_proj`가 hidden 차원을, gate/up이 model 차원을 본다는 확인이 중요합니다 —
이를 혼동하면 importance 벡터 길이가 틀리고 오차 계산 전체가 무의미해집니다.

보정 데이터는 wiki / code / chat 3도메인 층화 표본입니다. 단일 도메인 사용은
ACL 2024(arXiv:2311.09755)가 지적한 보정 의존성 문제를 피하기 위해 배제했습니다.

```bash
python3 collect_imatrix.py   --model allenai/OLMoE-1B-7B-0924   --revision <PINNED_SHA>   --domains wiki,code,chat   --samples 192 --seq-len 2048   --out artifacts/olmoe-imatrix.json
```

MoE 전용 종료 조건: 전체 토큰 수가 아니라 **각 layer × expert가 충분히 관측되었는지**로
판단해야 합니다(MoEQuant arXiv:2505.03804). 희귀 expert가 under-calibrated면
그 레이어의 민감도 점수를 신뢰할 수 없습니다. 현재 구현은 관측 토큰 수만 기록하므로
**expert coverage 계측이 다음 작업입니다.**

## 7. v0.3c: 실제 레이어별 민감도 (GPU 불필요, 완료)

OLMoE 레이어 0–11의 expert 0 gate/up 투영을 실제로 측정했습니다(레이어당 262,144 가중치 표본,
텐서 24개). 결과가 설계의 가정 하나를 **부분적으로 반증**하고 하나를 확인했습니다.

### 측정값

| 레이어 | STQ1_0 | LTC | LTC 이득 | 레이어 | STQ1_0 | LTC | LTC 이득 |
|---|---:|---:|---:|---|---:|---:|---:|
| L0 | 0.2477 | 0.2169 | +12.4% | L6 | 0.2541 | 0.2216 | +12.8% |
| L1 | 0.2471 | 0.2144 | +13.2% | L7 | 0.2467 | 0.2158 | +12.5% |
| L2 | 0.2486 | 0.2173 | +12.6% | L8 | 0.2574 | 0.2238 | +13.0% |
| L3 | 0.2477 | 0.2141 | +13.6% | L9 | 0.2578 | 0.2239 | +13.2% |
| L4 | 0.2478 | 0.2162 | +12.7% | L10 | 0.2518 | 0.2201 | +12.6% |
| L5 | 0.2476 | 0.2139 | +13.6% | L11 | 0.2536 | 0.2187 | +13.8% |

### 확인된 것: 깊이 단조성은 실재하지만 매우 약하다

`pearson(layer, stq_error) = +0.685` — 방향은 설계 가정과 일치합니다.
그러나 **레이어 간 전체 편차가 평균의 4.4%에 불과**합니다(min 0.2467, max 0.2578).

이것이 중요한 발견입니다. 설계 §3에서 저는 합성 민감도 모델
(0.22 + 0.30,	ext{depth}^2)를 썼는데, 이는 레이어 간 **136% 편차**를 만듭니다.
실제는 4.4%입니다. **제 합성 모델은 실제 민감도 분산을 30배 과장했습니다.**

결과적으로 레이어 선택은 설계가 상정한 것보다 훨씬 **약한 신호**에 기반합니다.
HY4의 29/48 분할이 재현하기 어렵다는 조사 결론과 일치합니다 — 신호가 약하면
보정 데이터가 조금만 달라져도 순위가 뒤집힙니다.

### 반증된 것: LTC 이득은 깊이와 무관하다

`pearson(layer, ltc_gain) = +0.241` — 이득이 12.4–13.8% 범위에 균일합니다.
따라서 LTC를 **일부 레이어에만 적용할 이유가 없습니다.** 전 expert 텐서에 균일 적용합니다.
설계 §8의 "부분 적용" 대안은 근거가 없으므로 폐기합니다.

### 확인된 것: top-k == Lagrangian (실측 데이터에서도)

실제 측정 오차로 두 할당기를 돌린 결과 **두 코덱 모두에서 배분이 완전히 동일**했습니다.
설계 §3의 결론이 합성이 아닌 실측에서 재확인되었습니다.

| 코덱 | top-k 오차 | Lagrangian 오차 | 동일? |
|---|---:|---:|---|
| STQ1_0 | 2.2554 | 2.2554 | 예 |
| LTC | 1.9955 | 1.9955 | 예 |

### 새로 발견된 것: 코덱을 바꾸면 레이어 맵이 바뀐다

| 코덱 | 저티어로 내려간 레이어 |
|---|---|
| STQ1_0 | 0, 1, 2, 3, 4, 5, 7, 10 |
| LTC | 1, 3, 4, 5, 7, 8, 9, 11 |

겹침 5/8. **LTC 도입 시 레이어 맵을 재계산해야 합니다.** 기존 STQ 맵을 재사용하면 안 됩니다.
이는 설계 §4의 "−40%까지 배분 불변" 결론과 상충하는 것처럼 보이지만, 그 결론은
합성 민감도(편차 136%)에서 나온 것입니다. 실제 편차가 4.4%로 작으므로 **작은 오차 변화도
순위를 뒤집습니다.** 설계 §4를 이 실측으로 교정합니다.

### IQ2 프록시의 한계 (정직한 기록)

제 IQ2 프록시는 7레벨(약 2.81비트 상당)을 쓰므로 **2.0625 bpw IQ2_XXS의 충실한 모델이 아닙니다.**
측정된 STQ/IQ2 오차비 약 3.9배는 실제 IQ2_XXS가 STQ1_0을 이기는 정도의 **상한**입니다.
순위 신호로만 사용해야 하며, 절대 오차비로 인용하면 안 됩니다.
실제 IQ2_XXS 인코더 구현이 v0.4의 필수 항목입니다.
