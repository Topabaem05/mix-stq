# MIX-STQ v0.4a 결과 — 바이트 형식 검증과 코드북 국소성

**작성일** 2026-08-29
**GPU 지출** $0 (v0.4a는 CPU만 사용)
**결론** 바이트 형식 **통과** (+7.2%). 그리고 코드북 국소성이 새로운 설계 축으로 드러났습니다.

---

## 1. 바이트 형식 구현과 검증

in-memory 코덱을 실제 저장 형식으로 구현했습니다.

| 구성 | 크기 | 내용 |
|---|---:|---|
| 블록 | **42 바이트** | fp16 scale 2 + 5비트 코드 × 64그룹 = 40 |
| 텐서 헤더 | **32 바이트** | 코드북. 각 바이트가 밑3 4자리 패턴 인덱스 (0–80) |
| payload bpw | **1.3125** | 42×8/256 |
| 실효 bpw (4M 가중치) | **1.312561** | 헤더 포함 |

검증 7항목 통과: 5비트 패킹 가역성, 코드북 헤더 왕복, 인코드·디코드 결정론,
블록별 삼진 격자 확인, STQ 제한 시 3:4 불변식 유지, bpw 정확성.

### 실제 가중치 + 실제 imatrix

| 텐서 | STQ1_0 | LTC | 이득 |
|---|---:|---:|---:|
| L0 gate_proj | 0.2759 | 0.2342 | **+15.1%** |
| L0 up_proj | 0.2886 | 0.2727 | +5.5% |
| L2 gate_proj | 0.2792 | 0.2603 | +6.8% |
| L2 up_proj | 0.2843 | 0.2702 | +5.0% |
| L4 gate_proj | 0.2716 | 0.2535 | +6.7% |
| L4 up_proj | 0.2856 | 0.2732 | +4.3% |
| **평균** | | | **+7.2%** |

6개 텐서 전부 양의 이득이며, bpw는 STQ1_0과 동일한 1.3151입니다.
v0.3b의 +6.5%와 일관되며, 바이트 형식이 in-memory 이득을 보존함을 확인했습니다.

## 2. 발견한 버그: 코드북 순서 불일치

바이트 왕복 테스트가 즉시 잡아낸 실제 버그입니다.

`serialize_codebook()`이 인덱스를 정렬해 저장하는데, 인코더는 `select_codebook()`이
반환한 **정렬되지 않은 순서**로 코드를 배정했습니다. 결과적으로 디코더가 다른 패턴을 참조했습니다.

| 단계 | 인코더 인덱스 (앞 8개) | 디코더 인덱스 (앞 8개) |
|---|---|---|
| 버그 | [0, 36, 18, 72, 30, 48, 6, 60] | [0, 1, 5, 6, 7, 8, 13, 17] |

증상: 상대오차 **2.289** (in-memory 0.319의 7배), 디코드 값이 삼진 격자를 벗어남.

수정: `canonical_codebook()`을 추가해 인코딩 **전에** 정렬 순서로 정규화합니다.
바이트 레이아웃이 유일한 진실 공급원이 됩니다. 수정 후 오차 0.304로 in-memory보다 오히려 낮습니다
(블록별 fp16 scale이 단일 전역 scale보다 정확하기 때문).

**이 버그는 in-memory 테스트로는 절대 발견할 수 없었습니다.** 직렬화 왕복만이 잡아냅니다.

## 3. 제 측정 절차의 오류도 발견했습니다

첫 v0.4a 실행이 +1.8%(2개 텐서 음수)를 보고했습니다. v0.3b의 +6.5%와 모순이라 조사했습니다.

원인은 형식이 아니라 **제 probe가 코드북을 1회만 적합**시킨 것이었습니다.
v0.3b는 `codec_fast.encode(learn=True)`로 3회 반복 적합을 했습니다.

| 방식 | L0 gate_proj | L2 up_proj |
|---|---:|---:|
| 3회 반복 적합 | +12.6% | +4.9% |
| 1회 적합 | +5.2% | **−0.5%** |

코드북과 scale의 교대 최적화가 **필수**입니다. `fit_codebook()`을 형식 모듈에 추가해
두 경로가 동일한 절차를 쓰도록 통일했습니다.

중간에 제가 "블록별 scale이 이득을 흡수한다"고 잘못 결론냈던 것도 기록합니다.
제 자신의 데이터(A +0.6% vs B +0.5%)가 그 가설을 반증했고, 실제 원인은 반복 횟수였습니다.

## 4. 새로운 설계 축: 코드북 국소성

코드북 하나가 몇 블록을 담당하는지에 따른 트레이드오프를 측정했습니다.
실제 가중치 + 실제 imatrix, L0 gate_proj 기준 (STQ1_0 = 0.2777 @ 1.3145 bpw).

| 코드북 범위 | 오차 | 이득 | bpw | 추가 bpw |
|---|---:|---:|---:|---:|
| 1 블록당 1개 | 0.2114 | **+23.9%** | 2.3125 | +1.0000 |
| 4 블록당 1개 | 0.2426 | +12.7% | 1.5625 | +0.2500 |
| 16 블록당 1개 | 0.2558 | +7.9% | 1.3750 | +0.0625 |
| **64 블록당 1개** | 0.2597 | **+6.5%** | **1.3281** | **+0.0156** |
| 256 블록당 1개 | 0.2636 | +5.1% | 1.3164 | +0.0039 |
| 텐서당 1개 (현재) | 0.2593 | +6.6% | 1.3145 | +0.0020 |

두 가지가 읽힙니다.

**블록당 코드북은 +23.9%까지 가지만 비용이 +1.0 bpw입니다.** 1.3125 → 2.3125 bpw는
IQ2_XXS(2.0625)보다 비싸면서 오차는 더 큽니다(0.2114 vs 0.0583). **명확히 열등한 선택**입니다.

**16–64 블록 구간이 흥미롭습니다.** 64블록당 코드북은 +0.0156 bpw로 +6.5%를 얻습니다.
다만 텐서당 1개(+0.0020 bpw)가 +6.6%를 내므로, 이 데이터에서는 **국소화 이득이 없습니다.**
국소성 곡선이 단조롭지 않은 것은 코드북 적합의 국소 최적 문제를 시사하며,
현재 권고는 **텐서당 단일 코드북 유지**입니다.
